# 技术方案说明:企业岗位经验 Skill 生成平台

## 1. 整体系统架构

```
┌─────────────────────────────────────────────────────┐
│                Web 界面(app.py, Streamlit)          │
│   ① 需求输入  ② Skill 配置展示  ③ 数据输入  ④ 报告展示   │
└──────────────┬───────────────────────┬──────────────┘
               │                       │
     ┌─────────▼─────────┐   ┌─────────▼─────────┐
     │ Skill 生成器        │   │ Skill 执行器       │
     │ (generator.py)     │   │ (executor.py)     │
     │ 元Prompt+校验+重试   │   │ Prompt组装+流式输出 │
     └─────────┬─────────┘   └─────────┬─────────┘
               │      ┌──────────┐     │
               ├─────▶│ Skill 资产 │◀───┤
               │      │ (JSON文件) │     │
               │      └──────────┘     │
     ┌─────────▼───────────────────────▼─────────┐
     │        Skill Schema(skill_schema.py)      │
     │        全平台统一的数据契约                   │
     └─────────────────────┬─────────────────────┘
                           │ OpenAI 兼容接口
                 ┌─────────▼─────────┐
                 │  LLM:GLM-4.7-Flash │
                 │  (智谱 BigModel)    │
                 └───────────────────┘
```

分层职责:界面层只做交互与渲染;生成器与执行器是两个独立引擎,共享同一份 Schema 契约;Skill 以 JSON 文件形式落地,是连接两个引擎的中间资产,可存储、可编辑、可分发。LLM 通过 OpenAI 兼容接口调用,底层模型可替换(架构上支持切换 DeepSeek、混元等,只需改 base_url 与 model 参数)。

模型选型:智谱 GLM-4.7-Flash。理由:官方长期免费、国内直连稳定无合规风险、200K 上下文与 128K 最大输出足以容纳完整 Skill 配置与长报告、支持流式输出。

## 2. LLM 在其中承担什么角色

LLM 承担**双重角色**,由两套不同的 Prompt 策略驱动:

**生成阶段——"Skill 架构师"。** 输入是用户的自然语言需求,系统提示词(元 Prompt)要求它以岗位资深专家视角,产出符合 JSON Schema 的结构化 Skill 配置。此阶段用低温度(0.3)保证结构稳定与输出可解析。

**执行阶段——"岗位专家"。** 系统动态组装 Skill 中的 Agent Prompt、分析流程与输出模板作为系统提示词,LLM 按其中定义的角色、框架与判断标准分析用户数据。此阶段温度略高(0.5),流式输出。

关键点在于:**执行阶段 LLM 的行为由 Skill 定义,而非由用户临场提问决定**——这正是"经验沉淀"的技术含义:专家经验被固化在 Agent Prompt 与分析流程里,任何人调用都得到同一套方法论。

## 3. 如何生成 Skill

生成链路四步:

**第一步,元 Prompt 约束。** 元 Prompt 中注入完整 JSON Schema,并施加内容质量规则:以岗位专家视角设计、分析流程须体现真实方法论(点名要求如漏斗拆解、同环比、异常归因)、输入字段须业务真实可得、Agent Prompt 必须包含角色/框架/判断标准/输出要求,以及数据纪律规则(详见第 4 节)。

**第二步,受约束生成。** 温度 0.3,要求只输出 JSON 本体,不允许解释性文字与 Markdown 代码块包裹。

**第三步,程序清洗与校验。** 剥离可能残留的代码块标记后做 `json.loads` 解析,再按 Schema 校验必填字段与嵌套结构(validate_skill 函数)。

**第四步,错误反馈重试。** 解析或校验失败时,将具体错误信息作为新一轮用户消息回传给模型("你的输出有问题:缺少必填字段 X,请修正后重新输出完整 JSON"),最多重试 3 次;仍失败则明确报错,不把不合格的 Skill 交给用户。

## 4. 如何避免 AI 生成错误的 Skill

采用**分层防御**,并明确每一层的能力边界:

**第一层:Schema 结构约束(防结构错误)。** 保证 Skill 形态合法——字段齐全、类型正确、机器可解析。由元 Prompt 注入 + 程序校验 + 重试闭环实现,已上线。

**第二层:Prompt 数据纪律(防编造数据)。** 开发中发现真实幻觉案例:执行报告中出现输入里不存在的"目标值 100000 元""同比 -9%"等虚构基准。治理方式是在元 Prompt 中强制每个 Skill 的 Agent Prompt 携带数据纪律规则:只使用用户实际提供的数据;未提供的信息(目标值、历史数据、同环比、行业均值)一律标注"未提供"或省略;所有计算注明过程。修复后经同一测试数据回归验证有效(治理前后报告对比存档于 docs/)。

**第三层:测试用例回归 + 专家评审(防业务错误)。** 继续测试暴露了 Prompt 治理的边界——它防得住"无中生有",防不住"有中算错":模型出现过用 GMV÷观看人数并称之为"转化率"(单位都不对)、把"粉丝流量占比 10%"误解为"新增粉丝 4800 人"等概念性错误。这类错误只有两种手段可靠:带预埋病灶的标准测试集回归,和领域专家人工评审。平台流程上要求 Skill 经专家审核才能发布。

**第四层(规划):确定性计算层。** 根治计算错误的方向是把算术从 LLM 手里拿走:输入数据先由代码完成指标计算与勾稽校验(如 GMV≈订单量×客单价),LLM 只基于算好的指标做解读、归因与建议。这是从 Demo 走向企业可用的最关键一步演进。

## 5. 如何实现 Skill 执行和评估

**执行**:executor.py 将 Skill 的 agent_prompt、analysis_steps、output_template 三段动态拼装为系统提示词,用户业务数据作为用户消息,调用 LLM 流式生成(stream=True,timeout 300s)。流式设计一举两得:避免长报告导致的读超时,同时让 Web 端逐字渲染、用户即时看到进展。报告按 output_template 的 Markdown 结构输出,支持一键下载。

**评估**(当前 + 规划):当前以"预埋病灶测试法"人工评估——构造内部勾稽一致、但埋有已知问题(低停留、低转化、流量结构失衡、爆款依赖)的测试数据,检验报告的病灶检出率与是否虚构数据。规划中的自动化评估包括:诊断覆盖率(检出预埋问题数/总数)、幻觉率(报告中无输入依据的数值占比,可用第二个 LLM 做裁判逐句核对来源)、格式合规率(是否符合输出模板)、以及线上用户评分与采纳率。评估结果回流驱动 Skill 迭代。

## 6. 已知局限与演进路线

诚实列出当前 Demo 的局限:LLM 直接做算术不可靠(需确定性计算层);Skill 生成质量依赖模型的领域常识,冷门岗位需专家介入更深;单并发免费模型不支持多用户同时使用(生产环境需付费档或私有化部署);数据以手工粘贴方式输入(需对接企业数据源)。演进优先级:确定性计算层 → 自动化评估流水线 → Skill 资产库(版本/权限/评分)→ 数据源直连。

这些局限本身验证了平台的核心命题:**企业需要的不是"更强的模型",而是"把模型约束在专家经验与工程护栏之内的系统"——这正是 Skill 相对于裸用 ChatGPT 的价值。**
